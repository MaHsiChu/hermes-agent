# ADR: OIDC identity and separately paired execution devices

Status: implemented; real signed-protocol tests pass. Deployed Keycloak and external network validation remain separate acceptance steps.

Use Authlib 1.6.9's Starlette OIDC client against Keycloak 26.8.0. Discovery, JWK signature verification, issuer/audience/time/nonce validation and Authorization Code with S256 PKCE are library responsibilities. We do not implement a password database, JWT parser, custom account crypto, or a production development-login bypass. Official references: [Authlib Starlette OIDC](https://docs.authlib.org/en/v1.6.9/client/starlette.html), [Authlib PKCE](https://docs.authlib.org/en/v1.7.0/oauth2/client/web/index.html), [Keycloak container deployment](https://www.keycloak.org/server/containers).

The relay stores temporary authorization flow data server-side with a ten-minute expiration, bound to an opaque HttpOnly cookie. Callback consumes the flow once before exchanging the code. Product identity keys are `(issuer,subject)`, not an editable email address. Provider tokens are discarded after verification. Product sessions are independent random cookies stored as SHA-256 hashes in SQL, expire after twelve hours by default, and are revoked on product logout. Cookie mutations require exact configured Origin and per-session CSRF token. Cookies are Secure outside explicit loopback development. Browser websocket admission checks cookie, Origin and expiration repeatedly. No long-lived credential is stored in JavaScript or localStorage.

The production example uses a confidential client; explicit public-client configuration uses Authlib's `token_endpoint_auth_method=none` and still requires S256 PKCE. Keycloak registration/recovery are disabled in the example: administrators invite users and must configure SMTP before enabling password recovery. Product logout ends this relay session, not the IdP SSO session. Administrative account suspension / IdP logout does not automatically revoke a still-valid relay cookie; its maximum remaining validity is the configured session lifetime. Back-channel logout is not implemented.

Device pairing is an application-level consent exchange after web OIDC login, not a claim of implementing OAuth RFC8628. A random device code remains on the PC. A short matching user code, expiration and explicit source subset are required before a one-time credential exchange. Source identity uses an unambiguous JSON tuple. Browser consent exposes only backend IDs, profiles and engines; tokens and local source roots remain private. Device credentials are independent from login sessions, stored hashed on the relay, and invalidate active device and relevant browser sockets immediately on revocation. The Bridge does not sync merely because someone logged in.

SQLAlchemy schema v1 uses SQLite only for explicitly configured local development and PostgreSQL for the production recipe. Relay copies are readable server-side; this is not end-to-end encryption. Backups therefore contain sensitive conversations and require the same access control as the live database. Native token/secret fields and known credential-shaped strings are filtered before durable copies/events; arbitrary secrets pasted into ordinary prose cannot be reliably detected. Sudo/secret/vault request payloads are not relayed. Operators must protect database and Bridge state directories, TLS keys and secret files.

One process owns relay websocket routing. Multiple relay workers or multiple Bridge instances sharing a device identity are not supported. Pinning container tags and Python hash-locked dependencies gives reproducibility; it does not replace security updates. No outbound telemetry is added.
